# Wenbu 增长与开源发布执行方案

编写日：2026-10-03。行动回执见 [发布核验](../reviews/growth-measurement-release.md)。下面的周期与门槛是计划，不是已经获得的流量、收录或用户增长。

## 产品定位与受众

问卜提供免费、可核对约定的传统命理工具，并帮助用户把模糊问题变成清晰的反思。中文核心表达：**先问清楚，再读结果**。英文：**A clear question. A considered reading.** 不把文化解释包装成科学预测，也不把免费描述成无限 AI 额度。

两条具体入口分别验证：

| 受众与任务                   | 获客入口                           | 第一次价值                                   | 下一步                         |
| ---------------------------- | ---------------------------------- | -------------------------------------------- | ------------------------------ |
| 第一次接触、想讨论眼前的问题 | 新手手册、塔罗、易经、Agent 引导   | 无需出生信息，得到一个结果和可回答的反思问题 | 保存结果、继续追问、读对应方法 |
| 研究命盘规则、需要复核输入   | 八字时区/换日/未知时辰指南         | 看到计算约定、已知与未知范围                 | 对照案例、导出结果             |
| Agent 使用者与开发者         | GitHub、MCP Registry、双语接入教程 | 固定六爻调用 + 完整资料读取                  | 安装 Skill、带所选上下文接入   |

## 立即执行的发布链

1. GitHub 主仓库主页、描述、topics 改为 wenbu.app；README 同时讲清使用入口、模型边界、许可、源码和接入。
2. 形成可直接使用的 `skills/wenbu/`、MCP 配置/请求样例、CLI 下载包，使用同一源码生成带 SHA-256 的 GitHub Release。不是为了外链创建空仓库。
3. 用户已创建 [wenbu-app 组织](https://github.com/wenbu-app)。已核对 Digidai 的 owner 权限并迁移 [主仓库](https://github.com/wenbu-app/wenbu)，保留仓库身份、提交与发布包；组织名称、简介与官网地址已设置。组织 profile 使用 `community/profile/README.md` 作为维护源，发布到组织的 `.github/profile/README.md`。迁移和接入发布的逐项回执见 [组织发布核验](../reviews/organization-launch-2026-10-03.md)。
4. 发布双语接入教程，保留固定输出、完整阅读、来源核验、个人输入与错误处理；在 Agents、Blog、README、站点页脚之间形成真实导航。
5. 通过主域 HTTP 公钥验证向官方 MCP Registry 发布 remote server 元数据。先核验线上工具，再提交版本；登记成功只说明目录可发现，不等于宿主安装、推荐排名或用户使用。
6. 部署后执行现有 IndexNow 提交与回执检查。Search Console/Bing Webmaster 的站点身份验证、sitemap 提交与实际收录分别记录；没有访问凭据时不虚构完成。

## 渠道链接与统计

闭合 campaign 白名单先于分发上线。GitHub 介绍链接用 `utm_source=github&utm_medium=referral&utm_campaign=open-source-2026`；Registry 网站链接用 `utm_source=mcp-registry&utm_medium=referral&utm_campaign=mcp-registry`。新手路径可用 `first-reading`。不采集任意查询参数、生日、问题、完整 referrer URL 或私人对话。

浏览器会话保留首次来源，30 分钟不活跃后重新建会话。来源是归因线索，不是经过认证的身份；无 referrer / UTM 的流量归入「无已知来源」，不能全部认定为用户主动输入域名。MCP/CLI 没有浏览器标识时只计调用，不能与网页人数相加。

## 7 / 14 / 30 天实验

| 周期        | 执行与观察                                                                       | 判断依据与下一步                                                                                           |
| ----------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 发布后 7 天 | 看 GitHub / Registry 引荐、工具调用渠道、完成使用的浏览器标识与错误              | 有点击却无使用：检查入口与首个例子；有使用且错误多：先修稳定性；零记录先检查采集覆盖，不能直接断言无人使用 |
| 14 天       | 按来源和进入页比较新手路径与开发者路径；查看真实搜索查询和曝光（需搜索站长后台） | 只扩展与真实卡点相关的教程；保留样本量，避免凭几个访问宣称渠道胜出                                         |
| 30 天       | 评估完整周期的去重浏览器标识、成功调用、保存/导出会话覆盖及重复使用              | 核对匿名 ID 30 天期限；不能把跨周期新增 ID 当作独立人数。再决定适合哪一个社区的高质量案例投稿              |

推荐核心信号是「服务器确认完成过使用的浏览器标识」，同时独立观察 CLI/MCP 非示例成功调用。它不是自然人、付费用户或预测效果。概览和明细采用同一时间/维度快照；去重标识不能把每天或渠道的数值直接加总。漏斗是同会话事件覆盖，不是严格有序转化；工具筛选可能移除 PV，因此不据此计算转化率。

## 暂不伪造的结果与后续条件

GitHub Org、Release、Registry、部署、IndexNow、搜索后台提交、实际索引、曝光与使用都有独立证据。目录被接收不等于获得流量。外部社区推广要围绕一个能复核的案例，而非反复发链接；需要具体账户、受众与发布内容才能执行账户内投稿。不进行付费购买、批量私信、链接交换或薄内容目录堆砌。
